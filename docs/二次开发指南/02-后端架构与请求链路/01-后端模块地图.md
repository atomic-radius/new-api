# 后端模块地图：文件、函数和数据责任

## 1. 进程入口与初始化

| 文件/函数 | 逐行阅读重点 | 输出或副作用 |
| --- | --- | --- |
| `main.go:40-150` `main` | 处理 `plugin` CLI、注册日志、调用初始化、设置 Gin、启动 HTTP 和信号退出 | 一个 Go 进程、HTTP listener、后台 goroutine |
| `main.go:291+` `InitResources` | 读取环境变量、初始化数据库/i18n/缓存/权限/任务 | 全局 DB、Redis、缓存和路由依赖 |
| `router/main.go` | 汇总 Web、API、Relay、插件和管理路由 | Gin 路由树 |
| `model/main.go` | 数据库初始化、AutoMigrate、连接池和 dialect 分支 | GORM `DB` 与 schema |

阅读启动代码时要记录“初始化顺序”：数据库和迁移必须先完成，之后才允许请求进入；缓存初始化失败不能被静默吞掉；多节点部署还要检查 `SESSION_SECRET`、Redis 和日志库。

## 2. 路由层

`router/relay-router.go:15-215` 是模型 API 的主入口。第 15-19 行安装 CORS、请求解压、body 清理和统计 middleware；第 21-43 行注册 `/v1/models`；第 71-80 行建立 `/v1` 公共前缀并安装 TokenAuth；第 80 行之后的 `ModelRequestRateLimit` 保护模型请求；第 91-181 行把具体路径映射到 RelayFormat；第 194-214 行处理 Gemini 特殊路径和 `:countTokens` 拒绝。

路由只选择协议和 middleware，不选择具体数据库 Channel。具体 Channel 在请求上下文已准备后由 `controller.getChannel` 调用 `service.CacheGetRandomSatisfiedChannel` 选择。

## 3. 请求解析层

`relay/helper/valid_request.go:22-61` 的 `GetAndValidateRequest` 依据 `RelayFormat` 分派：OpenAI、Gemini、Claude、Responses、图片、Embedding、Rerank、Audio、Realtime 各有独立 DTO。每个解析函数必须同时完成 JSON/multipart 解码、必填字段检查、上限检查和 body 可重放保存。

关键防线：`ExceedsMaxTokensLimit`（约 122-135 行）在计费算术前限制 token；图片编辑路径解析 multipart；Responses 必须有 `model` 和 `input`；Embedding 必须有 `input`。解析失败由 controller 映射为 400/413，不能进入渠道重试。

## 4. RelayInfo：一次请求的状态容器

`relay/common/relay_info.go:83-220` 的 `RelayInfo` 保存 token、用户、分组、原始模型名、计费模型名、RelayMode、请求 DTO、流状态、渠道元数据、价格快照、Billing session、重试错误和协议转换链。`GenRelayInfo`（约 692 行）把 controller 解析出的 DTO 与上下文合并成它。

调试时优先查看：`OriginModelName`（用户请求的模型）、`UpstreamModelName`（映射后的上游模型）、`BillingModelName`（计费身份）、`UsingGroup`（当前重试分组）、`RetryIndex`（第几次尝试）和 `RequestConversionChain`（协议转换路径）。

## 5. Channel 选择与能力表

`controller/relay.go:299-331` 的 `getChannel` 分两条路：已有 `ChannelMeta` 时使用 channel-test/固定渠道；普通请求调用 `service.CacheGetRandomSatisfiedChannel`，然后 `middleware.SetupContextForSelectedChannel` 把渠道类型、key、base URL、映射模型和覆盖参数写入上下文。`model/ability.go:108-173` 是数据库回源选择：按 group/model/enabled 查询，按 priority 降级，按 weight 随机选择，再读取 Channel。

因此新增模型时要区分“模型名存在”与“有可用 Ability”：模型列表由 Channel 能力和权限过滤产生，不是简单读取一个常量数组。

## 6. Controller 层的统一入口

`controller/relay.go:72-240` 是最重要的执行函数：

1. 72-91：保存 request id；Realtime 先升级 WebSocket。
2. 93-121：defer 统一错误输出；流已经写出 header 时改写为流内错误。
3. 123-131：调用 `GetAndValidateRequest`，把 body 错误映射到 400/413。
4. 134-152：调用 `GenRelayInfo`，注册性能指标和 panic 恢复。
5. 154-165：启动 Claude 心跳（如启用），调用 `PrepareRequestBilling`，注册最终失败退款 defer。
6. 167-181：创建 RetryParam，重置每次 attempt 的流状态和 output token。
7. 182-204：选 Channel、记录已用渠道、准备阶梯计费、恢复可重放 request body。
8. 206-215：按协议进入 `WssHelper`、`ClaudeHelper`、`geminiRelayHandler` 或 `relayHandler`。
9. 217-233：成功记录策略成功；失败规范化错误、记录策略、处理渠道失败并依据 `DecideRelayRetry` 决定是否继续。

## 7. 协议 Handler 与 Adaptor

`relay/compatible_handler.go:25+` 的 `TextHelper` 处理普通文本；图片、音频、Embedding、Rerank、Responses 和 Gemini 分别进入对应 handler。Handler 负责上游请求生命周期，`relay/channel/<provider>/adaptor.go` 负责 provider 的 URL、headers、请求转换、响应转换和错误转换；`relaykit/` 提供跨协议 DTO/converter。

不要把 provider 特有字段写入 controller；不要在 adaptor 直接操作用户余额；计费数量必须通过 `RelayInfo` 和统一 billing 流程回传。

## 8. 计费、日志和失败

`relay/request_billing.go:25-68` 先计算敏感词/token 元数据，再调用 `service.EstimateRequestToken`、`helper.ModelPriceHelper` 和 `service.PreConsumeBilling`。免费模型跳过预扣。`RefundFailedRequestBilling:72-81` 在所有 attempt 失败后退款并处理违规费用。

请求成功后还要完成实际 usage 结算、消费日志和性能指标；失败不能只看 HTTP 状态，必须检查是否已经预扣、是否已结算、是否需要退款。涉及这些文件时必须先阅读 `.agents/rules/billing.md`。
