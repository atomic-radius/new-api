# 一个模型调用的逐行链路

以下以客户端发送 `POST /v1/chat/completions`、模型为 `gpt-4o`、OpenAI 兼容上游为例。行号以当前源码为准，升级代码后应重新核对。

## 1. 路由到 Controller

1. `router/relay-router.go:71-75` 创建 `/v1` 路由组，执行 `RouteTag("relay")`、`SystemPerformanceCheck`、`TokenAuth`。
2. `router/relay-router.go:80` 后安装 `ModelRequestRateLimit`。
3. `router/relay-router.go:91-93` 建立 HTTP relay 子组并安装 `Distribute`。
4. `router/relay-router.go:105-107` 将 `/chat/completions` 的 handler 绑定为 `controller.Relay(c, types.RelayFormatOpenAI)`。
5. `controller/relay.go:72` 进入 `Relay`，第 74 行读取 request id。

`TokenAuth` 在进入 controller 前解析 Bearer Token、加载用户/分组/权限并把 token 信息写入 Gin context；如果失败，Relay 根本不会执行。`Distribute` 负责根据分组和分布策略准备请求上下文。

## 2. 读取并校验请求

6. `controller/relay.go:123` 调用 `helper.GetAndValidateRequest`。
7. `relay/helper/valid_request.go:22-27` 由 OpenAI format 进入 `GetAndValidateTextRequest`。
8. 该函数使用 `common.UnmarshalBodyReusable` 解析 DTO，并把原始 body 放入可重复读取的 BodyStorage；校验 model、messages/input、stream、max token 等字段。
9. 非法 JSON/缺字段返回到 `controller/relay.go:125-131`：普通请求 400，body 超限 413，并设置 `skipRetry`。

可重放 body 很关键：第一个 Channel 返回 429/5xx 后，第 194-204 行会重新从 BodyStorage 创建 `io.NopCloser`，第二个 Channel 读取的是同一份客户端请求，而不是已经被第一个 adaptor 消耗完的空流。

## 3. 创建 RelayInfo

10. `controller/relay.go:134` 调用 `relaycommon.GenRelayInfo`。
11. `relay/common/relay_info.go:692+` 根据 `RelayFormatOpenAI` 选择 `GenRelayInfoOpenAI`，把用户 ID、Token、原始模型名、请求 path、stream 标记、request DTO 和默认计费字段放入 `RelayInfo`。
12. 后续模型映射可能改 `ChannelMeta.UpstreamModelName`，但 `OriginModelName` 保留客户端模型，用于错误和计费审计；`BillingModelName` 独立保存价格身份。

## 4. 预扣费

13. `controller/relay.go:160` 调用 `relay.PrepareRequestBilling`。
14. `relay/request_billing.go:26-41` 构造 `TokenCountMeta`：必要时合并 prompt 文本；只需要价格数量时读取 max token/image count，避免无谓拼接。
15. `relay/request_billing.go:44-51` 执行敏感词检查；命中则写 RequestPolicy 事件并立即停止。
16. 第 53 行调用 `service.EstimateRequestToken`，第 57 行写入 `RelayInfo.estimatePromptTokens`。
17. 第 59 行调用 `helper.ModelPriceHelper`，计算模型倍率、用户组倍率、token/图片/工具数量和应预扣额度。
18. 第 67 行调用 `service.PreConsumeBilling`。非免费模型此时锁定额度；免费模型在第 63-65 行直接返回。

预扣成功并不等于最终扣费：上游可能返回实际 usage，结束时还要 settlement；所有 attempt 失败才由 `RefundFailedRequestBilling` 退款。

## 5. 选择 Channel

19. `controller/relay.go:177-181` 初始化 retry loop 和 `RetryIndex`。
20. 第 182 行进入 `getChannel`。
21. `controller/relay.go:315` 调用 `service.CacheGetRandomSatisfiedChannel`。
22. 缓存 miss 或回源时进入 `model.GetChannel`：`model/ability.go:115` 查询 group/model/enabled；第 119 行按约束过滤；第 130-149 行按 priority 选择重试层级；第 153-166 行按 weight 随机；第 171 行读取 Channel 实体。
23. `middleware.SetupContextForSelectedChannel`（`controller/relay.go:326`）把 channel type、base URL、key、映射名、覆盖参数、multi-key 信息写入上下文和 `RelayInfo.ChannelMeta`。

## 6. 发往上游

24. `controller/relay.go:194-204` 恢复 request body。
25. 第 206-215 行按 OpenAI format 调用 `relayHandler`，默认分支进入 `relay.TextHelper`。
26. `relay/compatible_handler.go:25+` 根据 Channel type 取得 adaptor，生成上游 URL、headers 和 body；必要时把 OpenAI 请求转为 Claude/Gemini/厂商 DTO。
27. adaptor 发送 HTTP 请求，记录首包时间和原始响应；流式请求由 stream scanner 逐块读取，转换器逐块写回 OpenAI SSE。
28. 非流式响应解析 usage、choices/tool calls 和 finish reason；流式末帧解析 usage（如果上游支持）或使用估算值。

## 7. 成功、重试和结算

29. handler 无错误返回到 `controller/relay.go:217-220`，写入 policy success 并结束 retry loop。
30. handler 有错误时第 223 行规范化错误，第 226 行调用 `service.DecideRelayRetry`。
31. 第 227 行记录策略失败，第 228 行更新渠道失败/自动封禁状态；只有 decision 为 retry 才回到下一次 attempt。
32. 所有 attempt 结束后，defer 在 `controller/relay.go:163-165` 调用 `RefundFailedRequestBilling`；成功路径则由响应处理和 billing session 完成实际结算。
33. 最外层 defer（93-121）统一写 JSON、Claude error 或流内错误，并附加 request id；第 146-151 行记录性能结果和 panic。

## 8. 调试断点清单

按顺序观察：`TokenAuth` context → `GetAndValidateRequest` DTO → `RelayInfo.OriginModelName` → `PrepareRequestBilling` PriceData → `getChannel` Channel ID → `ChannelMeta.UpstreamModelName` → adaptor outbound URL/header（脱敏）→ stream/response usage → billing settlement/log。任何一步缺失，都不要直接把问题归因于上游模型。
