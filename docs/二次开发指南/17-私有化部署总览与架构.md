# 私有化部署总览与架构

本文把 new-api 的代码、构建、镜像、运行数据和运维平台全部放在企业内网，目标是“代码不出内网、业务数据不出内网、发布过程可审计、生产可以回滚”。本文是部署设计文档，不代表当前仓库已经连接到某个真实 Kubernetes、MySQL、PostgreSQL 或 Redis 集群。

## 1. 私有化到底保护什么

私有化不是只把 Go 进程放到一台内网服务器，而是同时控制以下边界：

| 对象 | 私有化落点 | 不能出现的情况 |
| --- | --- | --- |
| 源码 | 自建 GitLab/Gitea，内网 Git | 源码推送到公共仓库 |
| CI Runner | 内网自托管 Runner | 使用未知的公共 Runner |
| 依赖和制品 | 内部 Go/Bun/npm/Docker 镜像代理 | 构建时任意访问公网 |
| 镜像 | Harbor 或 GitLab Registry | 生产直接拉取 Docker Hub |
| Kubernetes | 自建或私有云集群 | API Server 暴露公网 |
| 业务数据库 | 私有 MySQL/PostgreSQL | 数据库端口对公网开放 |
| 缓存 | 私有 Redis | Redis 无密码或公网可达 |
| Secret | Vault/KMS/External Secrets | 密码写入 Git、镜像或日志 |
| 日志监控 | Loki/ELK、Prometheus/Grafana 内网部署 | 日志上传到未知第三方 |
| 备份 | 内网备份服务器或私有对象存储 | 备份文件无加密地放在公网 |
| 上游模型 | 内部模型服务或受控出口 | 应用 Pod 任意访问互联网 |

## 2. 推荐网络拓扑

```text
开发者工作站
       │ HTTPS/SSH（内网）
       ▼
自建 GitLab ─── 私有 Runner ─── 内部 Registry/Harbor
                                      │ 镜像 digest
                                      ▼
                           Kubernetes 私有集群
                              │ Ingress/Service
                              ▼
                         new-api 多副本 Pod
                          ├─ 私有 MySQL/PostgreSQL
                          ├─ 私有 Redis
                          ├─ 私有日志与监控
                          └─ 私有模型服务/受控出口
```

new-api 本身从 `PORT` 读取监听端口，默认是 `3000`。多副本运行时，所有 Pod 必须使用同一主数据库、Redis、`SESSION_SECRET` 和 `CRYPTO_SECRET`；否则会出现会话、缓存、加密数据不一致。数据库支持 SQLite、MySQL 和 PostgreSQL，但生产多副本建议使用 MySQL 或 PostgreSQL，SQLite 只适合单实例或开发环境。

## 3. 三种网络隔离等级

### 完全内网

构建、Registry、Kubernetes、数据库、Redis 和监控都不能直接访问公网。需要预先同步 Go module、Bun 依赖、基础镜像、漏洞数据库、证书和系统补丁。安全等级最高，但依赖维护成本最大。

### 半离线

开发/构建区通过白名单代理访问外部，生产区无公网。外部依赖先进入隔离区，经漏洞扫描、许可证检查和人工批准，再推送到生产 Registry。这是安全与效率的最佳平衡，推荐大多数团队采用。

### 完全离线

没有公网出口、公共 DNS 和在线软件源。需要维护内部 Git、Registry、依赖镜像、时间同步、证书、漏洞库和补丁仓库。适合涉密或强监管环境，不适合没有专职运维团队的小团队。

## 4. 数据私有化链路

```text
浏览器/内部客户端
  → 私有 Ingress
  → new-api Service
  → Go Pod
      → SQL_DSN 指向私有 MySQL/PostgreSQL
      → REDIS_CONN_STRING 指向私有 Redis
      → 日志写入内网日志系统
      → 模型请求走内网模型或受控出口
```

必须执行：数据库仅允许应用 Namespace 的网段访问；Redis 仅允许应用和迁移 Job 访问；Ingress 强制 HTTPS；日志过滤 API Key、Cookie、Authorization、密码和模型敏感内容；备份加密并定期做恢复演练；生产禁止直接连接开发数据库。

## 5. 私有化组件分层

```text
代码层：GitLab Self-Managed
流水线层：GitLab Runner（rootless BuildKit/Kaniko）
制品层：Harbor 或 GitLab Container Registry
部署层：Kubernetes + Helm/Kustomize
密钥层：Vault + External Secrets（小规模可用 Kubernetes Secret 配合密钥加密）
数据层：MySQL/PostgreSQL + Redis
可观测层：Prometheus + Grafana + Loki/ELK
安全层：RBAC、NetworkPolicy、Pod Security、镜像扫描、Cosign 签名
```

第一阶段可以不引入 Argo CD，使用 GitLab CI 直接执行 Helm；规模扩大后再增加 Argo CD，把生产状态改成 GitOps 管理。不要一开始同时引入多个重复的 CI、CD 和密钥平台。

## 6. 部署前检查清单

- 内部 DNS、NTP、TLS 证书和私有 CA 已准备。
- GitLab、Runner、Registry 与 Kubernetes API 仅对管理网开放。
- Go、Bun、基础镜像和漏洞扫描数据库已有内部缓存。
- MySQL/PostgreSQL 已创建独立数据库和最小权限账号。
- Redis 开启认证、TLS（如环境要求）和网络白名单。
- `SESSION_SECRET`、`CRYPTO_SECRET`、数据库密码不进入仓库。
- Kubernetes Namespace、ServiceAccount、RBAC 和 NetworkPolicy 已创建。
- 备份任务、保留周期、恢复负责人和恢复演练记录已确定。
- 数据库迁移在 SQLite、MySQL、PostgreSQL 上分别验证；生产迁移前先备份。
